# Gegato Abecia Frontend API Documentation

This document consolidates the backend endpoints currently used by the frontend.
It is based on:

- the original API notes in `api (1).txt`
- the definition files in this folder
- the actual Angular services and mappers in `src/app/services` and `src/app/mappers`

## 1. Base URL

Primary host:

`https://gegato-abecia-fh.appspot.com`

Main API groups:

- Funeral service and charges: `https://gegato-abecia-fh.appspot.com/funeralservice`
- Payments: `https://gegato-abecia-fh.appspot.com/payments`
- Users/accounts: `https://gegato-abecia-fh.appspot.com/ua_control`

## 2. Frontend Request Behavior

### 2.1 Request headers sent by the frontend

When a user is logged in, the frontend interceptor adds these headers on requests sent to hosts containing `localhost` or `gegato-abecia`:

- `Authorization: Bearer {userId}`
- `X-User-ID: {userId}`
- `X-User-Role: {mappedRole}`
- `X-Username: {accountNumber or username}`

Observed mapped roles in the frontend:

- `SUPER_USER`, `ADMIN`, `ADMINISTRATOR` -> `Admin`
- `BILLER`, `STAFF`, `COLLECTOR`, `SUPERUSER` -> `Biller`
- `ACCOUNTING`, `ACCOUNTANT` -> `Accounting`
- `USER` -> `User`

### 2.2 Common backend quirks observed by the frontend

- Some lookup endpoints can return either a single object or an array.
- `find_record/{value}` is overloaded in several modules.
- It may behave as a numeric ID lookup.
- It may also behave as a text-filter search.
- Delete operations for funeral service, payments, and charges are called with `POST` plus an empty body, not HTTP `DELETE`.
- Date fields are normalized by the frontend. On save, most form dates are sent as Unix timestamps in milliseconds.
- User records may return fields under `username`, `userName`, or `accountNumber`.

## 3. Funeral Service API

Base path:

`/funeralservice`

### 3.1 Endpoints

#### GET `/find/{pageNo}/{recordsPerPage}`

Returns a paginated list of funeral service records.

Used by frontend for:

- deceased list
- admin dashboard contract analytics

#### GET `/find_record/{id}`

Fetches a single funeral service by numeric ID.

Observed behavior:

- the frontend treats the response as either a single object or an array containing one object.

#### GET `/find_record/{filter}`

Searches funeral service records by filter text.

Observed frontend usage:

- used by the deceased list search
- same endpoint path as the single-record lookup

#### POST `/save`

Creates or updates a funeral service record.

Create behavior:

- omit `id` or send no `id`

Update behavior:

- include `id`

#### POST `/delete/{id}`

Deletes a funeral service record.

Frontend sends:

- method: `POST`
- body: `{}`

#### GET `/find_by_burial/{startDate}/{endDate}`

Additional endpoint observed in the frontend service.

Purpose:

- fetch funeral services by burial date range
- used by schedule-related code

Recommended date format:

- `yyyy-mm-dd`

### 3.3 FuneralService save format used by the frontend

The frontend sends most date fields as Unix timestamps in milliseconds.

Example:

```json
{
	"id": 123,
	"contractNo": "FS-2026-001",
	"type": "Burial",
	"contractDate": 1777593600000,
	"dueDate": 1777852800000,
	"firstName": "Juan",
	"lastName": "Dela Cruz",
	"contractee": "Maria Dela Cruz",
	"contactNo": "09171234567",
	"dateOfBurial": 1777939200000,
	"cleared": false,
	"billingRemarks": "For partial payment"
}
```

## 4. Funeral Charges API

Charges use the same base group as funeral service.

Base path:

`/funeralservice`

### 4.1 Endpoints

#### GET `/find_charges/{funeralServiceId}`

Returns all charge rows for one funeral service.

Observed behavior:

- may return either an array or a single object
- frontend normalizes both into an array

#### POST `/save_charge`

Creates or updates a funeral charge row.

#### POST `/delete_charge/{id}`

Deletes a funeral charge row.

Frontend sends:

- method: `POST`
- body: `{}`

### 4.2 FuneralCharge shape

Source reference: `Definition-funeralCharges.txt`

Observed fields:

- `id`
- `funeralService`
- `chargeType`
- `description`
- `quantity`
- `unitPrice`
- `discount`
- `createdOn`
- `updatedOn`
- `createdBy`
- `updatedBy`
- `dueDate` -> source note says ignore this field

### 4.3 FuneralCharge save format used by the frontend

Important relation-field note:

- the frontend UI model uses `funeralContractId`
- the save payload maps that to backend field `funeralService`

Example:

```json
{
	"id": 1,
	"funeralService": 68725,
	"chargeType": "EXTRA",
	"description": "Flowers",
	"quantity": 2,
	"unitPrice": 500,
	"discount": 100,
	"createdBy": "admin"
}
```

## 5. Payments API

Base path:

`/payments`

### 5.1 Endpoints

#### GET `/find/{pageNo}/{recordsPerPage}`

Returns a paginated list of payments.

Used by frontend for:

- admin dashboard collection analytics

#### GET `/find_by_contract/{contractNumber}`

Returns payment records for one contract number.

Used by frontend for:

- funeral payment screen
- billing payment summary

Observed behavior:

- may return a single object or an array

#### GET `/find_record_service/{id}`

Legacy lookup by funeral service ID.

Used by frontend as a fallback when `find_by_contract` is unavailable.

#### GET `/find_record/{id}`

Fetches one payment by numeric payment ID.

#### GET `/find_record/{filter}`

Searches payments by text filter.

#### GET `/find_record_date/{start}/{end}`

Searches payments by date range.

Required format:

- `yyyy-mm-dd`

#### POST `/save`

Creates or updates a payment record.

#### POST `/delete/{id}`

Deletes a payment record.

Frontend sends:

- method: `POST`
- body: `{}`

### 5.2 FuneralPayment shape

Source reference: `Definition-FuneralPayment.txt`

Observed documented fields:

- `id`
- `controlNumber`
- `dateIssued`
- `checkDate`
- `issuedBy`
- `paymentType`
- `accountNumber`
- `amount`
- `description`
- `remarks`
- `checkCleared`
- `funeralServiceId`
- `orNumber`
- `arNumber`

Observed additional fields handled by the frontend:

- legacy alias handling for `bank` -> mapped to `paymentType`
- legacy relation alias handling for `serviced` -> mapped to `funeralServiceId`

### 5.3 Payment save format used by the frontend

The frontend sends payment dates as Unix timestamps in milliseconds.

Example:

```json
{
	"id": 45,
	"controlNumber": "OR-2026-104",
	"orNumber": "OR-2026-104",
	"arNumber": "AR-2026-104",
	"dateIssued": 1777593600000,
	"checkDate": 1777680000000,
	"issuedBy": "Accounting",
	"paymentType": "Check",
	"accountNumber": "CHK-001",
	"amount": 5000,
	"description": "Initial payment",
	"remarks": "Received at office",
	"checkCleared": true,
	"funeralServiceId": 123
}
```

Compatibility note:

- frontend now writes `funeralServiceId` and still supports legacy `serviced` during mapping
- frontend now writes `paymentType` and still maps legacy `bank` responses

## 6. Users or Accounts API

Base path:

`/ua_control`

### 6.1 Authentication behavior used by the frontend

There is no dedicated login endpoint currently used by the frontend.

Current login flow:

1. frontend calls `GET /ua_control/find_record/{username}`
2. frontend finds the matching returned record
3. frontend compares `password` on the client side
4. frontend stores the mapped user object in local storage

This means the backend account lookup endpoint is also serving login-related data.

### 6.2 Endpoints

#### GET `/find`

Returns all user accounts.

Observed usage:

- admin user management page
- admin dashboard role analytics

#### GET `/find_record/{id}`

Fetches one account by numeric ID.

#### GET `/find_record/{username}`

Fetches one account or matching accounts by username or account number.

Observed frontend usage:

- login lookup
- profile lookup
- admin user detail load

#### POST `/save`

Creates or updates an account.

Observed frontend usage:

- admin user editor
- profile update
- password change

Original source note:

- passwords should be encrypted before sending

### 6.3 Account shape observed by the frontend

Common fields observed in API responses:

- `id`
- `userId`
- `accountNumber`
- `username`
- `userName`
- `firstName`
- `lastName`
- `password`
- `position`
- `companyRole`
- `role`
- `roleText`
- `roleAccess`

### 6.4 User save format used by the frontend

The current frontend sends a broad account payload to `/save`.

Example:

```json
{
	"id": 52,
	"accountNumber": "ADMIN-002",
	"username": "ADMIN-002",
	"userName": "ADMIN-002",
	"firstName": "Tester",
	"lastName": "Tester",
	"companyRole": "SUPER_USER",
	"position": "Administrator",
	"roleAccess": 2,
	"password": "Admin"
}
```

Observed `companyRole` values used by the frontend:

- `SUPER_USER`
- `BILLER`
- `ACCOUNTING`
- `USER`

Mapped display roles in the app:

- `SUPER_USER` -> `Admin`
- `BILLER` -> `Biller`
- `ACCOUNTING` -> `Accounting`
- `USER` -> `User`

## 7. Date and Data Format Notes

### 7.1 Date search format

Use this format for date-range endpoints:

- `yyyy-mm-dd`

Example:

- `/payments/find_record_date/2026-05-01/2026-05-31`
- `/funeralservice/find_by_burial/2026-05-01/2026-05-31`

### 7.2 Save payload date format

The current frontend converts most form dates into Unix timestamps in milliseconds before sending them to the backend.

Examples:

- `contractDate: 1777593600000`
- `dueDate: 1777852800000`
- `dateIssued: 1777593600000`

### 7.3 Response format notes

The frontend is built to tolerate these backend variations:

- list endpoints returning arrays
- single-record endpoints returning a single object
- single-record endpoints returning an array with one record
- user endpoints returning an object
- user endpoints returning an array
- user endpoints returning an object containing a `data` array

## 8. Known Integration Notes

- `find_record/{value}` is overloaded for both numeric ID lookups and text search in multiple modules.
- Funeral service single-record lookup may return an array even when requesting by numeric ID.
- Charges save uses relation field `funeralService`, not `funeralContractId`.
- Payment definition and current frontend naming are not fully aligned for the relation field.
- User API originally notes that passwords should be encrypted before sending.
- The current frontend login flow performs password comparison on the client side after fetching the user record.
- Original notes mention missing or unclear funeral service fields: `dateOfBirth`, `dateOfDeath`, `church`, `cementery`, and `cremationDate`.
- Original notes also mention fields that may remain `null` even after insert or update: `deliveryDate`, `relationshipToDeceased`, `Embalmers`, and `flowerCarDriver`.
- Original notes question whether `collectorRemarks` should be treated as a boolean.
- There are spelling inconsistencies across the source notes and definitions, including `deliceryDate`, `checkDatel`, `Sting`, `emblamers`, and `cementery`.

## 9. Analytics Data Sources

These are the backend sources used or recommended for admin analytics:

- Total contracts: `GET /funeralservice/find/{page}/{size}`
- Service mix: `GET /funeralservice/find/{page}/{size}` using `type`
- Overdue contracts: `GET /funeralservice/find/{page}/{size}` using `dueDate` and `cleared`
- Upcoming burial or cremation schedule: `GET /funeralservice/find/{page}/{size}` using `dateOfBurial` and `cremationDate`
- Total collections: `GET /payments/find/{page}/{size}` using `amount`
- Payment trends by date: `GET /payments/find/{page}/{size}` or `GET /payments/find_record_date/{start}/{end}`
- User role counts: `GET /ua_control/find` using `companyRole`
